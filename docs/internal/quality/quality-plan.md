# Quality assurance plan

For any version and any output of `cxxgpr`, the following must remain traceable and reproducible from verification records and tool output.

1. Where is this specification (`REQ-*` / `DES-*` / `FMT-*`) tested, and what does it guarantee?
2. Which version, which commit, and which compiler / build configuration produced this numerical result?
3. When a version or dependency is updated, why and by how much did the baseline values change?

Each decision carries an ID (`QA-01` to `QA-10`), and consistency between specifications and tests is managed through the [traceability matrix](traceability.md).

## QA-01 Traceability

Requirements (`REQ-*`), design decisions (`DES-*`), persistence contracts (`FMT-*`), and quality contracts (`QA-*`) are defined in the respective specification documents and automatically mapped to tests and verification records.

- The traceability matrix `docs/internal/quality/traceability.md` is generated by `tools/qa/trace.py matrix`. Do not edit it by hand.
- Each GoogleTest case states the specification IDs it verifies, either as metadata or in a nearby comment (`// Spec: REQ-01, DES-05` / `RecordProperty("spec", "DES-05")`).
- Doxygen comments in the public headers `include/cxxgpr/` must not contain internal specification IDs (`REQ-`, `DES-`, `FMT-`, `QA-`, `M*-`); `just doc-check` rejects them.
- The gate `just trace-check` fails on references to undefined IDs and on any difference from the up-to-date `traceability.md`.

## QA-02 Verification records

Summaries of important numerical qualification and independent comparisons are recorded under `docs/internal/verification/<M-ID>/` (the PR that creates the record adds the directory). Collected verification records are not rewritten; a correction is added as a new record.

## QA-03 Baseline results (hexfloat baselines)

For capabilities that return numbers, baseline results are stored with fixed inputs in unrounded hexadecimal floating-point notation (hexfloat, `std::hexfloat`).

- They are placed in `qa/baselines/<case>/<platform>.json`.
- The first baseline case is `numeric-canary`. It evaluates IEEE-754 arithmetic, compensated summation, Eigen LLT factorization, elementary math functions, and deterministic random numbers, to detect even slight changes in the compiler, flags, Eigen, or the standard math library.
- Only `tools/qa/results.py accept` writes baseline results.

## QA-04 Result change management

**A change that alters a baseline result on a qualified platform by even one bit must not be merged without a [result-change record](result-changes/README.md).**

- `just results-check` compares the current build output with `qa/baselines/` and requires bitwise agreement on the same platform.
- Differences between different platforms (for example Windows MSVC vs Linux GCC; e.g. a 1 ulp difference in a standard math function) are tolerance-checked, qualified per platform as baselines, and recorded.

## QA-05 Meaning of versions

Versions are `MAJOR.MINOR.PATCH`.

| Component bumped | Changes allowed |
|---|---|
| `PATCH` | Bug fixes and internal improvements that do not change baseline results (bitwise agreement on all qualified platforms) |
| `MINOR` | Improvements within the numerical budget and feature additions (a record is required if results change), backward-compatible configuration additions |
| `MAJOR` | Breaking changes to the persistence format, the public API, or the numerical budget |

Before release, versions are treated as `0.x.y-dev`, keeping room to revise the public API until v1.0.

## QA-06 Provenance

`cxxgpr::build_info()` (implemented in M0-2) returns, in machine-readable form, the version, the Git commit SHA, the `uncommitted_changes` flag, the compiler name and version, the target OS and architecture, the build configuration (Debug / Release / Sanitize), the floating-point policy (`/fp:precise`, etc.), and the pinned versions of dependency packages. Baseline results are in principle collected on a tree with `uncommitted_changes == false`.

## QA-07 Environment qualification

The platform key is `<os>-<arch>-<compiler><major>.<minor>` (plus the relevant ABI / instruction-set settings). When `just results-check` runs on an unqualified platform or an updated compiler (for example a CI runner update), it fails immediately; the cause is investigated and, once qualification is recorded, the baseline is added.

## QA-08 Defects and known issues

Defect Issues state the scope of impact (kernel, precision policy, persistence compatibility) and the effect on baseline results. Known limitations are stated explicitly in `CHANGELOG.md` and in `README.md` / `README.ja.md`.

## QA-09 Pre-release quality gate

Before the REL-2 publication review, all of the following must be satisfied: all `just` gates pass, third-party headers are completely unexposed in `include/cxxgpr/`, the golden numerical comparison with `gprx` Exact GPR (fixed / fit / LOO / predict / persist) passes, the zero hot-path allocation tests pass, and `THIRD_PARTY_NOTICES.md` is consistent with `LICENSE`.

## QA-10 Roles and approval

Implementation and review verify from separate viewpoints. Specification changes (`design` Issues), approval of result-change records, and release tagging require the owner's approval. Agents do not merge or publish releases on their own.
