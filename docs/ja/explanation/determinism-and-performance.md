# 決定性と性能

cxxgpr は、ふつうは両立しにくい 2 つを約束する。ビット単位で再現できる結果と、高速で並列に動き、確保を行わない実装である。このページは、ライブラリがどうやって両方を得ているか、何が保証され何が保証されないかを説明する。読み物であり、実際の設定は {doc}`../how-to/optimize-performance` にある。

## ここでいう「再現できる」とは

再現性には段階がある。ある主張がどの段階の話かを、正確に区別しておくと役に立つ。

| 状況 | 同じ結果になるか |
|---|---|
| 同じプログラム、同じデータで、もう一度実行する | なる。ライブラリに隠れた状態、時計、シードのない乱数はない |
| 同じビルドで、OpenMP のスレッド数だけ変える | ビット単位で一致する。学習、予測、共分散、サンプリングのすべてで |
| 同じビルドで、等価な `FittedGpr`（コピー、`predict` と `predict_into`）を使う | 一致する |
| 同じソースで、コンパイラ、最適化レベル、OS、`CXXGPR_X86_ISA` を変える | 保証しない。結果は丸め誤差の範囲で一致するが、最後のビットまでは一致しない |
| 乱数列（`Xoshiro256PlusPlus::next_u64`）をプラットフォーム間で比べる | 一致する。整数演算だけでできているため |

3 行目と 4 行目があるから、ライブラリは fast-math なしで、ビルドごとに命令セットを固定してビルドされる。1 つのビルドの中では、演算は IEEE の演算の固定した列である。保証するのは、スレッドがその列を変えないことである。

## 決定的な並列縮約

浮動小数点の加算は結合的ではない。各スレッドが自分の分を足してから部分和を合わせる並列の総和は、スレッド数ごとに丸めのパターンが変わる。この差は、コレスキー分解と最適化器を通るうちに大きくなり、ハイパーパラメータの目に見える違いになる。cxxgpr は、結果に寄与する浮動小数点演算の順序を、スレッド数に左右させないことで、これを避ける。

方針は 2 つの部分からなる。

**独立した列。** 行列の各列（または列ブロック）を、ちょうど 1 つのスレッドが、同じ入力から、1 スレッドで計算するときと同じ命令列で計算するように、仕事を割り当てる。どのスレッドが担当するかは問題にならない。ある列の値はほかの列に依存しないからである。

**固定した順序での直列の結合。** 列を 1 つの数にまとめる必要があるとき（たとえば勾配の 1 要素は、行列全体にわたる和 $\langle W, \partial K/\partial\theta\rangle_F$ である）、各スレッドは自分の列の寄与を、事前確保した配列の専用のスロットに書く。その後、1 つのスレッドが、列番号の昇順に、Neumaier の補償付きで足し上げる。

```{mermaid}
flowchart LR
  subgraph par ["並列フェーズ: 独立した列"]
    T0["スレッド 0: 列 0..a"] --> P0["partial[0..a]"]
    T1["スレッド 1: 列 a..b"] --> P1["partial[a..b]"]
    T2["スレッド 2: 列 b..n"] --> P2["partial[b..n]"]
  end
  P0 --> S["直列フェーズ: partial[0], partial[1], ... partial[n-1] を<br/>この順に、Neumaier の補償付きで足す"]
  P1 --> S
  P2 --> S
  S --> R["結果: スレッド数によらず同一"]
```

公開ヘルパーの `linalg::parallel_lower_reduce_cols` は、まさにこのパターンを実装している。自分の総和にも使える（{doc}`../how-to/use-low-level-building-blocks`）。部分和の配列は、`WorkspaceCore` が事前確保する `col_partials` バッファである。そのため縮約も、確保を必要としない。

### 均衡のとれたブロック

下三角のループは、仕事量が不揃いである。$n \times n$ 行列の第 $j$ 列には $n - j$ 個の要素がある。列を同じ幅のブロックに分けると、先頭のブロックを担当するスレッドの仕事が多くなりすぎる。`linalg::lower_area(n, c)` は、先頭の $c$ 列にある要素数を数える。

$$
\text{area}(c) = c\,n - \frac{c(c-1)}{2},
$$

`linalg::lower_block_start(n, i, B)` は、累積の面積が全体 $n(n+1)/2$ の $i/B$ に最も近くなる列を返す。$n = 1000$ を 4 ブロックに分けると、境界は 0、134、293、500、1000 になる。最初のブロックは少数の長い列からなり、最後のブロックは多数の短い列からなる。境界の計算には、オーバーフローしない整数演算を使う。

分割はスレッド数に依存するが、結果は依存しない。上の 2 つの規則があるからである。ブロック化したコレスキー分解と、多数の右辺を持つ三角求解も同じである。スレッド数が変えるのは、どのスレッドがいつブロックを計算するかであり、1 つの値を生む演算の列は変わらない。

### 決定性が及ばない範囲

実行ごとに変わる利用者側の要素は、再現性を壊す。シードのない乱数の入力、学習データの行の順序の違い、別のビルドがそうである。スレッド数そのものは OpenMP を通じてライブラリの外で設定されるので、モデルの一部にはならない。

## 乱数

cxxgpr の乱数はすべて明示的で、シードを指定する。事後サンプル（`FittedGpr::sample` と、workspace API の `sample`）、最適化器の再スタート、`FastSimulatedAnnealing` がこれにあたる。乱数は `Xoshiro256PlusPlus`（`SeededRng` という別名もある）から引く。状態が小さく、統計的な品質がよい 256 ビットの生成器である。64 ビットのシードは SplitMix64 で 4 つの状態語に展開される。0 や 1 のようなシードでも、離れた乱数列になる。

- `next_u64()` は整数演算だけでできており、どのプラットフォームでも同じ列を返す。生成器は Xoshiro256++ である。
- `unit()` は上位 53 ビットを取り、$[0, 1)$ にスケールする。この変換は正確で、移植性がある。`open_unit()` は、その値を 0 と 1 から少なくとも $2^{-53}$ だけ離すように丸め、対数が有限に保たれるようにする。
- `up_to(max)` は、Lemire の棄却法で、$[0, \text{max}]$ の偏りのない整数を引く。
- `unit_normal()` は、Box-Muller 変換で標準正規乱数を作る。C ライブラリの `log`、`sqrt`、三角関数を呼ぶので、C ライブラリが違うと、1 つの値の最後のビットが変わることがある。基礎の整数列は同一である。

生成器はコピーも比較（`operator==`）も安価なので、保存した状態から乱数列を再現できる。

モデルのサンプルは、$z \sim \mathcal{N}(0, I)$ を引いて $\mu_* + L_* z$ を返す。$L_*$ は事後共分散のコレスキー因子である。したがって、同じモデルと同じシードなら、スレッド数によらず同じサンプルになる。

## 確保の方針

ヒープ確保は遅く、アロケータの内部でロックを取り、遅延の予測もできない。同じ $n \times n$ の問題を何百回も評価する最適化ループでは、純粋な無駄でもある。そこで cxxgpr は、最初に 1 回だけ確保し、あとは再利用する。

```{mermaid}
flowchart LR
  A["fit() の開始:<br/>n 点分をすべて確保"] --> B["最適化ループ:<br/>値、勾配、ヘッセ行列<br/>(確保なし)"]
  B --> C["fit() の復帰:<br/>学習用バッファを解放"]
  C --> D["FittedGpr が L, alpha, X と<br/>QueryWorkspace を保持"]
  D --> E["predict_into, 1 回目:<br/>ワークスペースが拡張される"]
  E --> F["predict_into, 2 回目以降:<br/>確保なし"]
```

図の背後にある規則は次のとおり。

- **学習用バッファは 1 回で確保する。** `FitBuffers<P>` は `fit` の開始時に $n$ を知り、行列、スクラッチ、（任意で）距離キャッシュを 1 度に確保する。例外はヘッセ行列用のスクラッチである。最も大きなバッファ（$n \times n$ の行列が $p$ 個）なので、最初のヘッセ行列の計算で確保される。2 階微分を使わない最適化器は、その代価を払わない。
- **ループの内側では何も確保しない。** 周辺尤度と勾配の評価はバッファを再利用する。カーネル木は、コンパイル時に深さが求まった `NestedBuffers` に評価結果を書く。
- **学習用メモリは最後に解放する。** `FittedGpr` が保持するのは、予測に必要なものだけである。
- **予測用メモリは単調に増える。** 最初の呼び出しで `QueryWorkspace` の大きさが決まり、同じ大きさのバッチの以降の呼び出しは、それを再利用する。

保証が及ぶのは、ホットパスである。勾配つきの負の対数周辺尤度の評価と、ウォームアップ後の `predict_into` である。新しいオブジェクトを返す呼び出し（`predict`、`predict_covariance`、`sample`、`loo_predict`）は、結果を確保しなければならない。保証はテストで機械的に検査している。Eigen は `EIGEN_RUNTIME_NO_MALLOC` つきでビルドされ、監査対象の範囲で内部の確保が起きると異常終了する。それ以外は、グローバル `operator new` のカウンタが捕らえる。

### トレードオフ

事前に確保するということは、反復が必要とする量より少なくても、最大の問題の分のメモリを確保済みにするということである。支配的なのは密行列で、倍精度の $n \times n$ 行列は $8n^2$ バイトを要する。$n = 1000$ で 8 MB、$n = 10\,000$ で 800 MB である。`FitPolicy` を使うと、時間を多少犠牲にして節約型を選べる（{doc}`../how-to/optimize-performance`）。`SinglePrecision` と `MixedPrecision` は行列の記憶域を半分にする。厳密推論の $O(n^3)$ の時間と $O(n^2)$ のメモリは避けられない。確保の方針が決めるのは、それがどれだけ予測しやすいかだけである。

## SIMD カーネルと命令セット

負荷の高いループは SIMD 向けに書かれている。密行列の線形代数は Eigen が受け持ち、cxxgpr はその上に、カーネル葉の指数関数、非有限値の検査、パックされた三角積、距離計算のための独自のベクトル化カーネルを追加している。これには 3 つの段階があり、ライブラリのコンパイル時に選ばれる。

| 段階 | 選択方法 | 典型的なハードウェア |
|---|---|---|
| AVX-512 | `-DCXXGPR_X86_ISA=AVX512` | 最近のサーバー向けと一部のデスクトップ向け CPU |
| AVX2 と FMA | `-DCXXGPR_X86_ISA=AVX2`（x86-64 の既定） | 2013 年ごろ以降のほとんどの x86-64 CPU |
| SSE2 | `-DCXXGPR_X86_ISA=SSE2` | すべての x86-64 CPU |

64 ビット Arm では、cxxgpr のカーネルは移植性のあるフォールバックを使い、このオプションは存在しない。実行時のディスパッチはない。段階はコンパイル済みライブラリの一部であり、AVX2 向けにビルドしたライブラリは、AVX2 のない CPU では動かない。融合積和演算とベクトル幅の違いは丸めを変えるので、2 つの段階の結果は、丸め誤差の範囲では一致するが、ビット単位では一致しない。冒頭の表の 4 行目がこれである。選び方は {doc}`../reference/build-options` を参照。

高速指数関数 `KernelExp::FastApprox` は、これらのカーネルの内側で、速度と精度のどちらをとるかを独立に選ぶ設定である。`std::exp` の代わりに、範囲縮約つきの 7 次多項式を使う。結果は相対で $10^{-5}$ の水準で変わるので、利用者が明示的に有効にする方式にしている。

## 厳密さには時間がかかる

補償付きの総和、固定した縮約の順序、fast-math なし、直列の結合ステップには、少なからず速度の代償がある。直列のフェーズは、$O(n^3)$ の因子分解の仕事のあとに続く $O(n)$ または $O(n^2)$ の加算なので、スケーリングの妨げにはならない。{doc}`../how-to/optimize-performance` の測定でも、決定的な実装のまま、16 スレッドで 4 倍から 6 倍の高速化が得られている。ライブラリが再現性を優先するのは、コア数で結果が変わる学習済みモデルは、テストも、デバッグも、信頼も難しいからである。
