# 互換性

cxxgpr が動く環境、版番号の付け方と、版番号が約束する内容、ライブラリと利用側のプログラムとで揃えておくべきものを説明する。ここに書く事実は、プロジェクトのビルドファイル、継続的インテグレーション、品質方針から取ったものである。テストされていない、あるいは約束されていない事項は、そう明記する。

## 対応ツールチェーン

| 項目 | 対応 | 非対応またはテストなし |
|---|---|---|
| 言語標準 | C++23。`std::expected` とそのモナド的な関数が使えること | C++20 以前 |
| MSVC | Windows 11 上の 19.44 以降（Visual Studio 17.14 以降） | それより古い MSVC は、構成時に拒否される |
| GCC | Linux 上の 14 以降 | それより古い GCC は、必要な標準ライブラリの機能が足りない |
| Clang | テストなし | 標準ライブラリが `std::expected` を提供すれば構成できる可能性はあるが、プロジェクトは Clang でビルドもテストもしていない |
| オペレーティングシステム | Windows 11 と Linux（継続的インテグレーションは、Windows Server 2025 と Ubuntu 24.04 のランナーを使う） | macOS などはテストしていない |
| プロセッサ | x86-64（既定は AVX2。AVX-512 と SSE2 を選べる） | Arm。CMake は `arm64` を認識するが、プリセットも、実行したテストもない |
| ビルドシステム | CMake 3.25 以降、Ninja、vcpkg のマニフェストモード | ほかのジェネレーターも動くかもしれないが、検証しているのは Ninja だけ |

テストの構成は次のとおり。Linux で GCC 14 の Debug、Release、AddressSanitizer と UndefinedBehaviorSanitizer つきのビルド、そして Windows の MSVC である。要件とオプションの詳細は {doc}`build-options` にある。

## API の安定性

cxxgpr は、`MAJOR.MINOR.PATCH` の版番号を使う。現在のリリース系列は `0.1` である。

:::{important}
1.0 より前の版は、プレ 1.0 のリリースである。プロジェクトは、バージョン 1.0 までは、公開 API を改訂する権利を明示的に留保している。これには、既定のテンプレート引数と補助的な診断フィールドも含まれる。厳密な版を固定し、アップグレードの前に変更履歴を読むこと。
:::

番号のどの部分でどんな変更を許すかについての、プロジェクトの方針は次のとおり。

| 上げる部分 | 許される変更 |
|---|---|
| `PATCH` | 基準結果を変えない、バグ修正と内部の改善（検証済みのすべてのプラットフォームでビット単位に一致） |
| `MINOR` | 数値予算の範囲内の改善と、機能追加。結果が変わる場合は、変更を記録する。設定への後方互換な追加 |
| `MAJOR` | 永続化フォーマット、公開 API、数値予算に対する破壊的な変更 |

1.0 より前では、これらの記述は意図であって保証ではない。`0.x` のリリースは API を壊すことがある。1.0 以降は、ソース互換性を壊してよいのは `MAJOR` だけになる。

1.0 より前でも、設計上、安定しているものは次のとおり。

- エラーの契約。関数は `std::expected<T, GprError>` を返し、API の境界を越えて例外を投げない。
- 列優先の入力と、`Gpr` と `FittedGpr` の分離。
- 永続化フォーマットの版（`persist::FORMAT_VERSION`。現在は 1）。`format_version` が異なるディレクトリを読むと `UnsupportedPersistVersion` を返す。自動的な移行はない。{doc}`file-format` を参照。
- 公開ヘッダーに、Eigen、nlohmann/json、OpenMP の型を含まない（{doc}`../explanation/design-principles`）。

## CMake での版

`find_package(cxxgpr 0.1.0 CONFIG REQUIRED)` は `SameMinorVersion` の規則を使う。要求した版より古くない、インストール済みの `0.1.x` を受け入れ、`0.2.0` や `1.0.0` を拒否する。1.0 より前は、マイナーバージョンで API が変わりうるので、これは意図した動作である。

`cxxgpr::build_info()` は、リンクしたライブラリの版と、正確な git コミットを報告する。

## ABI

cxxgpr は、C++ のインターフェースを持つ C++ の静的ライブラリである。版をまたぐ ABI も、ツールチェーンをまたぐ ABI も約束しない。

- **更新のたびに再ビルドする。** ライブラリの新しい版、新しいコンパイラの版、変更したコンパイラオプションは、型のレイアウトと装飾名を変えうる。対応するヘッダーとライブラリに対して、プログラムを再ビルドする。
- **ビルド構成を揃える。** ライブラリとプログラムは、同じ C++ 標準ライブラリの実装を使わなければならない。Windows では、同じ C ランタイム、同じデバッグ／リリースの設定（イテレーターデバッグと `_ITERATOR_DEBUG_LEVEL`、`/MD` か `/MT` かの選択）も揃える。Release のライブラリを Debug のプログラムと混ぜると、MSVC では失敗する可能性が高い。
- **重いテンプレートは、4 つの精度ポリシーについてライブラリ内にインスタンス化されている。** `FitBuffers`、`WorkspaceCore`、`QueryWorkspace`、`LeafCache`、`predict_into` などの workspace 関数は、`DoublePrecision`、`SinglePrecision`、`MixedPrecision<PromoteStorage>`、`MixedPrecision<ReevaluateKernel>` について `extern template` で宣言されている。ほかのポリシーは、`PrecisionPolicyConcept` がコンパイル時に拒否する。
- **OpenMP ランタイム。** ライブラリが OpenMP つきでビルドされていれば、最終的なリンクには、同じコンパイラの OpenMP ランタイムも必要である。
- **共有ライブラリはない。** ビルドされるのは静的ライブラリだけなので、プロセス間で安定に保つべきバイナリインターフェースはない。

## 数値の互換性

結果は、{doc}`../explanation/determinism-and-performance` の規則のもとで再現できる。1 つのビルドの中では、スレッド数が違っていてもビット単位で一致する。コンパイラ、OS、`CXXGPR_X86_ISA` の段階が違えば、丸め誤差の範囲で一致する。`Xoshiro256PlusPlus` の乱数列は、どこでも同じ整数列であり、同じシードなら `gprx` と一致するよう定められている。

保存したモデルは、プラットフォームをまたいで使えることを意図している。ディスク上のフォーマットは、リトルエンディアンのヘッダーと列優先の行列を持つ safetensors のレイアウトである（{doc}`file-format`）。別のプラットフォームで読み込んだモデルは、元のモデルと丸め誤差の範囲で同じ予測を返すと期待される。

## gprx との関係

cxxgpr は、Rust ライブラリ `gprx` の Exact GPR の部分を実装する。永続化フォーマットも、`gprx` と本質的に互換である。疎なモデルとオンラインのモデルは cxxgpr の対象外で、読み込み時に拒否される。範囲は {doc}`../explanation/relationship-to-gprx` を参照。

## ライセンスとサードパーティのコード

cxxgpr は Apache-2.0 でライセンスされる。依存ライブラリは、それぞれのライセンスを保つ。Eigen は MPL-2.0 で、`EIGEN_MPL2_ONLY` により MPL-2 の部分に限っている。nlohmann/json は MIT である。OpenMP はコンパイラに付属する。ライセンス文と告知は `share/cxxgpr` にインストールされ、`THIRD_PARTY_NOTICES.md` に列挙されている。
